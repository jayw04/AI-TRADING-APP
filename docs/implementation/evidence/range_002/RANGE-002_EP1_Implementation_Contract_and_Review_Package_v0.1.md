## 1. Contract: `_bind` semantics

**Binding contract summary (all five points are required; the refusal order includes step 1b and the `TypeError` outcome, see 1.1):**
1. `_bind` calls the **merged** `results_guard.require_capability` and **propagates its refusal unchanged** (it never catches, wraps or downgrades `InvalidCapabilityError`). The refusal order is fixed: step 1 first; then step 1b, where caller arguments of the wrong **type** raise `TypeError`; then steps 2 to 6, where validly typed but unauthorized inputs raise `CapabilityBindingError`.
2. `_bind` uses the **existing authoritative** `PHASE_PARTITIONS` of the governance model (read at call time); it owns no phase, partition or window table.
3. The capability interface is **statically type-safe**: attributes are read from the object returned by `require_capability` (inferred return type); fallback is a private `typing.Protocol`; a `getattr` is allowed only with a written justification in the PR and never to hide a typo.
4. `_bind` checks the **requested date range** against `capability.date_range` and, when given, the **run identity** (`expected_run_id`).
5. `_bind` **never constructs, copies, caches, returns or revives** a capability; it returns `None`.

Details follow.


`engine/_causality.py` would contain one private helper and one exception class. Signature (sketch, PROPOSED):

`_bind(capability: object, *, spec_sha256: str, allowed_phases: tuple[Phase, ...] | frozenset[Phase], expected_run_id: str | None = None, requested_range: DateRange | None = None) -> None`

It returns nothing. It never constructs, copies, caches or returns a capability. Order of checks. Three distinct outcomes: step 1 raises the guard's own `InvalidCapabilityError`, **propagated unchanged**; step 1b raises `TypeError` for caller arguments of the wrong **type** (a programming defect); steps 2 to 6 raise `CapabilityBindingError` for validly typed but **unauthorized** inputs. All fail closed:

| Step | Check | Source of truth |
|---|---|---|
| 1 | The object is a genuine capability **and its run is still OPEN in the registry it was issued against** | The merged public function `results_guard.require_capability(capability)` is called, not re-implemented. It already refuses: a non-capability, a look-alike, a forged object, a copy, and a closed/failed/aborted/mismatched run. This is the "run state" check |
| 1b | Explicit up-front argument type checks (section 1.1), run only after step 1 has accepted the capability | `type()`/`isinstance` on the four caller arguments |
| 2 | `capability.spec_sha256 == spec_sha256` | public slot |
| 3 | `capability.phase in allowed_phases` | public slot |
| 4 | **Defense in depth (not a separate authorization boundary):** `capability.partition` is a **member** of the frozenset `PHASE_PARTITIONS.get(capability.phase)`; if the table has no entry for the capability's phase, `_bind` refuses with `CapabilityBindingError` (it never lets a `KeyError` escape). Membership, not equality, because the table values are frozensets. There is no caller-supplied partition set: the only caller restriction is `allowed_phases` (step 3) | public slot, `governance.model.PHASE_PARTITIONS` |
| 5 | If `expected_run_id` is given: `capability.run_id == expected_run_id` (cross-run refusal) | public slot |
| 6 | If `requested_range` is given: `capability.date_range.contains(requested_range)` | public slot, `DateRange.contains` |

**Phase and partition tables are READ from the guard, never copied.** Step 4 reads `governance.model.PHASE_PARTITIONS` through a module alias (`from app.research.range002.governance import model as governance_model`, then `governance_model.PHASE_PARTITIONS[...]` at call time), and `allowed_phases` is built by the caller from `Phase` members. `_bind` contains no literal phase or partition name, no copied mapping, and no date window of its own (windows come only from `capability.date_range`, which the guard fixed at issuance). This matters because the current table (`P3A -> DEVELOPMENT_SELECTION`, `P3B -> DEVELOPMENT_CONFIRMATION`) encodes the unsigned Addendum A1 split; a copy would hard-code that layout, and the guard's table can change with the addendum. Test: a test replaces `PHASE_PARTITIONS` on the model module with a different mapping (monkeypatch) and shows that `_bind` follows it; a static test asserts the strings `DEVELOPMENT_SELECTION`, `DEVELOPMENT_CONFIRMATION`, `HOLDOUT`, `REPLAY_RNG001` and `PAPER` do not occur in `_causality.py`. Mutation M13 (copy the mapping into `_bind`) must be killed by the monkeypatch test.

**Typing without breaking mypy or the lint.** A parameter annotated `object` has no attributes for mypy, and the lint forbids naming `ResultsCapability` (R-C). Specified approach: `_bind` takes `capability: object`, then uses the **return value of `require_capability`** (declared to return the genuine, validated capability) as the object whose attributes it reads: `checked = require_capability(capability)`; every later check reads `checked.spec_sha256`, `checked.phase`, `checked.partition`, `checked.run_id`, `checked.date_range`. mypy infers the type from the function's return annotation, so the source never names the type, no `getattr` is needed and no cast is needed. Fallback if the inference is not accepted by mypy in this repository's configuration: a private `typing.Protocol` (`_CapabilityFields`) declaring those five read-only attributes, with `checked: _CapabilityFields = require_capability(capability)`; plain `getattr` on an untyped `object` is NOT used because it would hide attribute typos. `mypy app/research/range002` must pass in the PR evidence.

Properties the contract requires: no memoization of a past success (each call re-reads run state through step 1); no I/O of its own; only public governance names imported (`require_capability`, `GovernanceError`, `InvalidCapabilityError`, `DateRange`, `Phase`, `PHASE_PARTITIONS`); parameter annotated `capability: object` (lint R-C: the type name is not referenced); no public constants built by a call (R-A2); no underscore-private governance name (R-B).

**1.1 Argument types and malformed input (F5).** Decision: wrong argument **types** raise `TypeError`; validly typed but unauthorized inputs raise `CapabilityBindingError`; the guard's refusal for the capability itself stays `InvalidCapabilityError`. Justification: `_bind` is private and called only by engine entry points written in this repository, so a wrong type is a programming defect, not an authorization outcome; collapsing it into `CapabilityBindingError` would make a caller bug indistinguishable from a refusal (the owner asked to keep them distinct) and invite callers to catch the refusal class and carry on. `TypeError` still fails closed (it stops the run). `authorize` uses a domain error at `results_guard.py:677` because its caller is an external orchestrator; the explicit-check style is mirrored, the exception class is not. The checks (step 1b) are explicit and exact, with no broad exception handling anywhere in the module:
- `spec_sha256`: `type(spec_sha256) is str` (a malformed but string value simply fails step 2 as unauthorized);
- `allowed_phases`: `type(allowed_phases)` is `tuple` or `frozenset`, and every element satisfies `type(item) is Phase`. A `str` or `list` is rejected. This matters: `Phase` is a `StrEnum`, so a bare string such as `"P3A"` passed as `allowed_phases` would make `capability.phase in allowed_phases` a **substring test** and could silently authorize the wrong phase. An empty tuple/frozenset is validly typed and simply refuses at step 3;
- `expected_run_id`: `None` or `type(expected_run_id) is str`;
- `requested_range`: `None` or `type(requested_range) is DateRange` (exact type, as at `results_guard.py:677`; a datetime pair, tuple or dict is rejected).
The `capability` argument itself is not type-checked (it is `object`); step 1 decides. Because step 1 runs first, a wrong-typed argument together with an invalid capability raises the guard's `InvalidCapabilityError`, never `TypeError`. A static (AST) test asserts `_causality.py` has no bare `except`, no `except Exception` and no `except BaseException`: the module masks nothing.

**1.2 Step 4 is defense in depth, not an independent control (F1).** `require_capability` already compares the run's registry row `(spec_sha256, phase, partition)` with the capability's (`results_guard.py:331-332`), and `authorize` refuses a partition outside the phase's set (`results_guard.py:668`; `run_registry.py:474` does the same when a run is opened). A genuine capability therefore cannot carry a partition outside `PHASE_PARTITIONS[phase]`, so step 4 can only ever refuse if the table `_bind` sees diverges from the guard's. The PR text, docstrings and evidence **must not describe step 4 as an independent authorization boundary or as a separate control**; it is a consistency check kept as defense in depth. This is why M4 cannot be killed with a real capability (below).

**1.3 Missing phase in the table (F3).** `_bind` reads the table with `.get(capability.phase)` and refuses with `CapabilityBindingError` when the result is `None` (and when the partition is not a member). A raw `PHASE_PARTITIONS[phase]` index, which would leak `KeyError` as an unclassified failure, is the mutant M15.

**1.4 Table access pattern versus the actual lint rules (F4).** Verified by reading `tests/research/range002/governance/test_import_lint.py` (the R-A to R-E rules in its docstring and the implementation around lines 498-565): rule R-B flags only imports of, or attribute access to, **underscore-private** names of a governance module (`_is_private`), including `getattr(module, "_x")`. `PHASE_PARTITIONS` has no leading underscore, so reading it is allowed. The lint nowhere consults a module's `__all__` (no occurrence in the test file), so the fact that `governance/model.py:15` lists only `["MAX_ATTEMPT_LIMIT", "DateRange", "Partition", "Phase"]` and omits `PHASE_PARTITIONS` does not make the read a violation; `__all__` affects only `from ... import *`. Permitted pattern recorded: `from app.research.range002.governance import model as governance_model`, then `governance_model.PHASE_PARTITIONS.get(...)` at call time. A direct `from ...governance.model import PHASE_PARTITIONS` would also pass the lint but would bind the object at import time, defeating the call-time lookup the M4/M13 tests rely on, so it is not used. Residual uncertainty: the lint resolves aliases generally and no rule treats a non-`__all__` public name specially, but it is not exercised on this exact pattern today; the settling evidence is the planned test `test_lint_accepts_governance_model_public_attribute_read` (runs `lint_source` on a copy of the `_causality.py` source) plus the existing real-tree test `test_real_range002_tree_complies` passing in the PR.

**1.5 Docstring and comment trap in `engine/_causality.py` (verified).** The lint walks every AST node, and the string-constant branch of `tests/research/range002/governance/test_import_lint.py` (the `isinstance(node, ast.Constant) and isinstance(node.value, str)` block at about lines 531-535) flags any string constant containing `ResultsCapability` or `__wrapped__`. A module or function docstring is a string constant, as is every exception message and every f-string literal part, so a docstring that merely mentions either word fails the lint. Comments are not AST nodes and are ignored by the lint. Separately, this contract's own static test forbids the partition names (`DEVELOPMENT_SELECTION`, `DEVELOPMENT_CONFIRMATION`, `HOLDOUT`, `REPLAY_RNG001`, `PAPER`) anywhere in `_causality.py`, and that test scans the **raw source text**, so it also catches comments. Therefore docstrings, exception messages **and comments** in `_causality.py` must avoid all of: `ResultsCapability`, `__wrapped__`, and the five partition names. Describe things generically ("the capability", "the phase table", "a protected partition"). The same applies to the `Protocol` fallback of section 1 if it is ever used.

**Rejections the tests must prove**
- copied (`copy.copy`, `copy.deepcopy`): refused by the capability's own `__copy__`/`__deepcopy__`;
- serialized (`pickle.dumps`): refused by `__reduce__`;
- forged: a look-alike object with identical attributes; `ResultsCapability(object(), ...)` without the issue token; `object.__new__(ResultsCapability)` with attributes set around the immutability guard (outside the threat model, but it must still fail step 1 because the weak registry table does not contain it);
- expired: run closed (`close_run`) after issuance;
- cross-run: a capability issued for run A used with `expected_run_id` of run B, and a capability for spec A used with spec B's hash;
- wrong phase, range outside `date_range`, range straddling the boundary by one day;
- wrong partition: **not reachable with a real capability**, because `authorize` issues only partitions that `PHASE_PARTITIONS` assigns to the phase. The test must therefore use a monkeypatch that REMOVES the real capability's partition from `PHASE_PARTITIONS[capability.phase]` (restored by the fixture) and asserts `_bind` raises `CapabilityBindingError`. **Isolation of this monkeypatch:** it is confined to synthetic unit tests and uses the pytest `monkeypatch` fixture, which restores automatically. It replaces the module attribute with a **new copied dict** (`monkeypatch.setattr(governance_model, "PHASE_PARTITIONS", patched_copy)`), so the production dict and its frozensets are never mutated, not even temporarily; `_bind` reads the attribute through the module alias at call time, which is why the replacement is visible to it. There is **no runtime means of changing authorization rules**: `_bind` has no parameter, setter or hook that accepts a table, and a static (AST) test asserts that nothing under `app/` assigns to, augments, rebinds or `setattr`s `PHASE_PARTITIONS`, **except** three existing, exempted bindings on current main: the single definition at `governance/model.py:38` and the two import bindings at `governance/results_guard.py:181` and `governance/run_registry.py:69` (the test matches these by AST shape, a module-level definition in `model.py` and `from ... import PHASE_PARTITIONS` in those two modules, not by line number, so the exemption survives unrelated edits). Any other binding anywhere fails the test. A companion test snapshots `PHASE_PARTITIONS` (a deep copy) at module import, runs the monkeypatched test body, calls `monkeypatch.undo()` explicitly, and asserts that `PHASE_PARTITIONS` is equal to the snapshot and is the same object as before (`test_phase_partitions_unchanged_after_monkeypatch`); an autouse module-level fixture repeats the comparison at teardown.

**Direct-call requirement (M1, M8, M9).** The `requires_capability` decorator refuses a closed run before the body runs, so a mutant of `_bind` that drops the run-state call, memoizes a success, or swallows the refusal would SURVIVE if `_bind` were only exercised through a decorated function. The killing tests for M1, M8 and M9 must call `_bind` **directly** (not through any decorated function): M1 a closed-run capability passed straight to `_bind` must raise `InvalidCapabilityError`; M8 a direct success, then the run is closed, then a second direct call must raise; M9 a direct refusal must propagate as the original exception type (a swallow-and-return mutant makes the call return). **The M9 refusal case must raise `CapabilityBindingError`** (for example a wrong spec hash with a valid open-run capability): the M9 mutant swallows only `CapabilityBindingError`, so an `InvalidCapabilityError` refusal (which comes from `require_capability`) would not separate the mutant from the original and must not be the case used for M9.

**Direct tests exercise `_bind` itself.** Each M1/M8/M9 killing test binds the name `target = _causality._bind`, asserts `target is _causality._bind` and `not hasattr(target, "__requires_capability__")`, and calls `target(...)` with a capability obtained from the real `authorize`. No decorated function, helper wrapper or harness shim sits between the test and `_bind`, so an earlier decorator refusal cannot hide a missing check inside `_bind`.

**All 18 mutations are meaningful and distinguishable.** Each mutant must behave differently from the original `_bind` (or `assert_causal`/harness) on at least one concrete input, and each has a named killing test (mapping below). The mutator run records, for every mutant, the killing test and the failing assertion. A mutant found to be **equivalent** (no input separates it from the original) is a **plan defect, not test weakness**: it is removed or redefined by an amendment to this plan before the push request, never excused by weakening a test. M14 was handled this way after the first review of this contract.

**M11 must discriminate causal from look-ahead specifically.** The M11 fixture uses one record set, one cut and one adversarial replacement for two functions: a **causal control** (several pre-cut outputs, none reading post-cut data), which must pass `assert_causal`, and the **look-ahead variant** (first pre-cut output causal, a later pre-cut output depends on post-cut data), which must fail. `assert_causal`'s failure message is **required to name the FIRST differing output position (its index)**, and the M11 test asserts that index is a later pre-cut position (index 1 or greater, never the first output), so a failure cannot come from an unrelated cause (fixture error, non-determinism, a wrong cut). **Why M18 is technically necessary (it is not added merely because the ordering test was strengthened).** The ordering requirement is: with a capability that `require_capability` refuses (for example its run is closed) **and** wrong-typed arguments, `_bind` must raise the guard's `InvalidCapabilityError`, because step 1 precedes step 1b. Checked against every existing mutant, none changes behaviour on exactly that input in a way that the ordering test could attribute to ordering:

- **M14** (read attributes before `require_capability`): a genuine closed-run capability has readable attributes, then `require_capability` still raises `InvalidCapabilityError`, the same as the original, so the ordering test passes under M14.
- **M1** (remove the `require_capability` call): different behaviour (no run-state refusal), but it is killed by the direct closed-run test and says nothing about ordering.
- **M17** (broad `except` re-raising `CapabilityBindingError`) does fail the ordering test, but only incidentally (the wrong class comes back); a correct-class implementation with the wrong order would not be caught by it.
**M18** (run the step 1b type checks before step 1) is the only transformation that separates the two orders. **Non-equivalence, exact input:** a capability whose run has been closed, together with `spec_sha256=123` and `requested_range=("2026-03-02", "2026-03-06")` (an `int`, and a tuple that is not a `DateRange`; both are rejected by step 1b). The test must use a genuinely closed-run capability (obtained from the real `authorize`, then the run closed through the registry), call `_bind` directly (not through a decorated function), and assert the exact exception type `InvalidCapabilityError`. Folding the case into M14 or M16 was considered and rejected: each mutation entry must be a single code transformation, and M14 and M16 are different transformations with different distinguishing inputs.

## 4. Deliberate look-ahead failure through `assert_causal`

`tests/research/range002/_causal.py`: `assert_causal(run_fn, records, cut)` (its failure message must name the first differing output position, see the M11 paragraph) runs `run_fn` on the true records and on a copy in which every record with `available_at > cut` is adversarially altered (extreme values, reordered, and one variant with those records deleted), then asserts that all outputs with `decision_at <= cut` are identical. Required tests: (a) a causal synthetic function passes; (b) a **deliberately look-ahead** function (for example a decision that reads the maximum over all records including future ones) makes `assert_causal` fail (`pytest.raises(AssertionError)`); (c) a look-ahead that peeks by index rather than value also fails; (d) a function whose output depends on record order only after the cut still passes. The helper uses stdlib `random.Random(seed)` only.
