## Two findings recorded SEPARATELY from this PASS

Neither invalidates the result; both are tracked as follow-ups rather than folded into B3a.

1. **Deployment-proof tooling defect.** The version-write payload attempted to assert
   `.deploy_src_sha` from *inside* the container. That marker is **not mounted there** — neither
   `/app/.deploy_src_sha` nor the host path exists in the container — so the assertion was incapable of
   proving what it claimed, and `if os.path.isfile(...)` made it **fail open** instead of refusing.
   The required identity was subsequently established independently (host-side marker = `.deploy_src_sha`
   = `956e932`; DB version = runtime version = `1.0.3`), which is what preserves A3's conclusion.
   Follow-up: make the host-side marker check authoritative and **fail-closed**.
2. **`WORKBENCH_LOG_LEVEL` durability.** Effective runtime is INFO and correct today, so this is not a
   Strategy-8 activation blocker. But a backend-only rebuild never touches `.env`, and
   `provision-from-s3.sh` rebuilds `.env` from SSM — so the manually appended line is lost at the next
   full provision. Follow-up: create `/workbench/prod/WORKBENCH_LOG_LEVEL=INFO` as a governed
   infra/config change **before** the next `provision-from-s3.sh` run.
